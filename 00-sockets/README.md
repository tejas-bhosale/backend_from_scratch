## Explanation by LLM

**File descriptor, concretely.** Every process has a small table the kernel maintains for it (on Linux, reachable as `/proc/<pid>/fd/`). Each slot in that table is a number — 0, 1, 2 are always stdin/stdout/stderr — pointing to a kernel-side object: a regular file, a pipe, or a socket. `socket()` doesn't return the socket itself; it returns the *index* into this table. Every `recv()`/`send()`/`close()` you call is really "kernel, look up slot N in my table and act on whatever's there." That's why the number `client_socket` holds isn't the connection — it's a lookup key.

**Why a socket is "treated as a file."** This isn't a workaround or an optimization — it's the actual Unix design: *any* kernel object that implements a common interface (read bytes, write bytes, close) gets a slot in the same fd table and answers to the same syscalls. A regular file and a TCP socket are different structs internally, but from your process's point of view they're both just "a number I can read from and write to." That uniformity is why `recv()`/`send()` feel like `read()`/`write()` — under the hood on Linux they largely are.

**Why `accept()` hands back a different object than the listening socket.** Your original socket (the one you called `bind`/`listen` on) has one job: sit in the kernel's connection queue and produce new connections. Each call to `accept()` pops one finished handshake off that queue and wraps it in its own fd — that's the object your thread reads/writes to. The listening socket never touches data; it just keeps manufacturing new fds. That's why you correctly noticed "it creates a new object for this specific connection" — that observation was right.

**The `b''` vs. `BrokenPipeError` mechanism, in full.** TCP has two distinct ways a connection ends, and the kernel reports them differently to your code:
- A **graceful close** (the other side calls `close()` normally, or the process exits cleanly) sends a FIN packet — "no more data is coming, but nothing's broken." Your next `recv()` on that socket returns `b''` immediately. It's not an error; it's the kernel telling you the stream ended cleanly. This is what you saw when the client finished its 10-loop and closed.
- An **abrupt kill** (`kill -9`) gives the process zero chance to run any shutdown code — the kernel just deallocates everything that process held, sockets included, mid-anything. From the *other* machine's (or process's) point of view, the connection didn't get a polite goodbye; it just stopped answering. The next time you try to *write* into that dead connection, the kernel already knows there's no one to deliver it to, and refuses — that's the `BrokenPipeError [Errno 32]`. Notice it surfaced on `send()`, not `recv()` — writing into a known-dead connection fails immediately, whereas reading from one that quietly disappeared (rather than closing cleanly) can even hang, which is closer to what you saw during the earlier "commented out `close()`" experiment.

**The `Ctrl+C` / threading result — your explanation was on the right track, here's the precise reason.** `Ctrl+C` sends `SIGINT` to the process, and Python raises `KeyboardInterrupt` only in whichever thread was actually running/blocked at that instant — in your case, the **main thread**, sitting in `accept()` waiting for a new connection. Your already-running `handle_client` thread was blocked in its own `recv()` call, on a different thread, and never saw that interrupt at all. Separately, `threading.Thread()` defaults to **non-daemon**, meaning the Python process won't fully exit while any such thread is still alive — so even after the main thread died from the unhandled exception, the worker thread kept running its loop to completion before the process finally exited. So it's not quite "the thread kept running because it's handled by multithreading" — more precisely: **the interrupt only ever reached the main thread**, and the worker thread was both unreachable by that specific signal delivery and structurally allowed to outlive the main thread's death.
